## 0. 为什么是"运行时编辑器"

这个工具的全部价值在于**改完立刻开玩**。独立编辑器要来回切窗口、要重启、
要重新读档 —— 而那正是验玩法时最费时间的一段。做进游戏里之后，循环变成：

```
F1 → 改一个数字 → 抬头看桌上的牌变了 → F1 → 接着拖牌试
```

用户拍板的四条（开工前问过）：

| # | 决定 | 选择 |
|---|---|---|
| 1 | 编辑何时落盘 | **改动立即生效，显式保存才落盘**；顶栏显示"未保存" |
| 2 | 「画区域」怎么做 | **在游戏画布上拖矩形**（编辑器给一个模式） |
| 3 | 改了定义，桌上的牌 | **立刻全部重画** |
| 4 | 删掉还有实例在用的定义 | **拦住**，并告诉你有几张在用 |

## 1. 数据地基：卡组（M5 第 1 步）

**发现的问题**：牌库那 20 张的张数配方（5/5/4/4/2）**写死在 `DemoContent.BuildDeck` 的代码里**。
于是"把火球术从 5 张改成 3 张试试"这件事要改代码、重新编译、重启、重新摆桌 ——
而验玩法最常做的恰恰是这件事。

**处置**：新增 `CardDeck` / `CardStack`（`scripts/Data/CardDeckData.cs`），
进 `SaveProject.Decks`（`project.json` 那一半，不是 `state.json`）。

```jsonc
"decks": [
  {
    "id": "demo.deck.starter",
    "displayName": "示例卡组",
    "cards": [ { "cardId": "demo.fireball", "count": 5 }, … ]
  }
]
```

三条约定：

1. **卡组只存 id，不存卡面。** 改卡面数值时整副牌跟着变 ——
   而验玩法时你改的正是"那张卡的费用"，改完还要立刻看到整副牌都变了。
2. **行的次序 = 发牌次序。** 于是不洗牌时"牌库顶"是可预期的，自检能直接推期望值。
   摊开逻辑收在 `CardDeck.Expand()`：产品与自检读同一个方法，
   否则"发出来的牌序对不对"会有两套各自成立的说法。
3. **`DemoContent` 的写死配方收口到 `CreateStarterDeck`。**
   两份各自维护的配方迟早会长得不一样（示例桌面 vs 新建存档）。

### 抓到的真 bug：`totalCards` 被写进了 `project.json`

`CardDeck.TotalCards` 是算出来的属性，`System.Text.Json` **默认会把只有 getter 的属性写出去**、
读的时候又静默丢弃。于是存档里多一行 `"totalCards": 20`，而且它会与 `cards` 漂移 ——
手改文件的人把 `count` 从 5 改成 3，那一行还写着 20。

同一个坑在 `ZoneDefinition.Center` 与 `BoardTheme.BoardRect` 上**各踩过一次**。
这次是新写的断言 `deck_total_is_not_serialized` 当场抓住的（第一次跑就红）。

> 这条断言不需要"回退验证"就已经自证了：它直接命中了那个输出。
> 反过来验证（加 `[JsonIgnore]` → 变绿）同样成立。

## 2. 定义改动 → 桌上实例立刻重画（M5 第 2 步）

**机制**：`ObjectManager.ApplyCardDefinition(def)` / `ApplyTokenDefinition(def)`

```
定义池[id] = def  →  遍历场上每个实例，SetDefinition(def)  →  发 CardDefinitionChanged 信号
```

三条不能省的细节：

- **只 `QueueRedraw` 是不够的。** 卡画的是它**持有**的那份定义；定义池里换了新对象、
  卡还指着旧的，重画出来还是老样子。
- **实例级覆盖（`FieldOverrides`）刻意不动。** 改的是定义（模板），
  不该把"这一张和别的不同"的手改数值冲掉。
- **`CountCardInstances` 是决定 4 的实现。** 删定义前先数一数还有几张在用。

## 3. 图片导入（M5 第 3 步）

`ImageImport.Copy(saveName, sourcePath)` → 返回**存档内的裸文件名**（写进定义的就是它）。
`ImageImport.ResolvePath(fileName)` 负责把裸文件名拼成完整路径。

三条约定：

| 约定 | 理由 |
|---|---|
| 定义里只存**文件名**，不存路径 | 存档目录可以整个拷走（"自包含存档"的另一半） |
| **重名不覆盖**（`face.png` → `face_2.png`） | 覆盖是"改一张卡的面，结果另一张也变了"那类极难往回查的问题 |
| 内容相同**复用**同一个文件名 | 反复导入同一张图不该堆出三份一模一样的文件 |

**拷贝逻辑是纯的（只用 `FileAccess`），不碰 UI。** 于是自检能直接断言
"字节真的进去了、名字对不对" —— 而不是"我点了一次 FileDialog 看着像成功了"。
`FileDialog` 只是它的一个调用方。

### 顺带修掉的一个老 bug

`Board.ApplyTheme` 原来走 `ResourceLoader.Exists/Load` 加载背景图，
而**导入的图放在存档目录里，不在 Godot 的资源系统里** —— 也就是说
"桌面背景图"这条路从 M1 起就没生效过。现在改走 `TextureStore`（同一套路径解析）。

### 踩到的坑：临时文件不能放 `user://`

自检要造一张 PNG 来验导入，最初写在 `user://selfcheck_import.png` ——
**沙箱里 `user://` 不可写**（M4 就是为这件事加的 `--save-root`），
`Image.SavePng` 报 `FileCantOpen`，整节被跳过。
而那一节的 `skipped` 看起来和"导入功能坏了"一模一样。

处置：临时目录放**存档根的兄弟目录**（`<saveRoot> 的上一级/_selfcheck_tmp`），
跑完自己删掉 —— 探针不许在工作区里留痕迹。

## 4. 编辑器外壳与五个分页（M5 第 4 步）

```
EditorPanel (Control，挂 HUD 这一层)
├── PanelContainer
│   └── VBoxContainer
│       ├── Header（标题 + "未保存" + 关闭）
│       ├── TabContainer
│       │   ├── CardEditorPage    卡牌：卡池列表 + 预览 + 基本/字段/版式三段表单
│       │   ├── TokenEditorPage   指示物：列表 + 四形状预览 + 属性 + 放到桌面
│       │   ├── DeckEditorPage    卡组：配方表 + 一键发牌
│       │   ├── BoardEditorPage   桌面：背景/底色/尺寸/网格
│       │   └── ZoneEditorPage    区域：画矩形 + 全参数
│       └── Footer（状态摘要 + 保存按钮）
└── ZoneDrawOverlay（铺满视口，画区域用；挂在 HudRoot 下、面板之后）
```

### 卡面预览不需要另写一遍渲染

`CardFaceRenderer.DrawFace(CanvasItem, CardDefinition, Rect2)` 从 M2 起就是
**静态纯函数 + `_Draw`**（而不是搭一棵 `Control` 树）。于是预览只是
**换一个 `CanvasItem` 再画一遍** —— 桌上那张卡与预览框里的卡来自同一个函数，
不可能出现"预览好看、桌上不一样"这种最让人不信任编辑器的症状。

正反两面都画：卡背也是要调的东西，而它只在盖放的牌上看得出来。

### Token 预览：把画法抽出来，而不是抄一份

Token 原来把画法写在 `TokenObject.DrawContent` 里。编辑器要预览只有两条路：
**抄一份**（迟早分叉）或者**抽出来**。选了后者：新增 `TokenFaceRenderer`，
与 `CardFaceRenderer` 同构（静态纯函数），`TokenObject` 与编辑器预览都调它。

四种形状在预览里并排全画、当前那一档加描边 —— 形状是 Token 最关键的一眼特征，
而选它要来回试；只画当前那一个的话，换形状得反复点下拉才看得出区别。

### 「画区域」为什么必须是铺满视口的遮罩层

面板只占屏幕的一块，而区域要画在桌面的**任何地方**。画在页里的话，
拖到面板外面预览框会当场消失（半个矩形），看起来像拖拽断了。

遮罩层挂在 `HudRoot` 下（与面板同级、排在它之后），在 `ViewportController` 之上，
于是它的 `_GuiInput` 先收到事件。这与 `PopupMenu` 挡事件的机理是同一个 ——
只不过那次它是麻烦、这次它是工具。

三件事必须做对：

1. **吃掉鼠标按下**（`AcceptEvent`）：否则画一块区域会顺便把一张牌拖走了。
2. **屏幕 ↔ 桌面都走相机**：自己算"除缩放"的话，缩放一变预览框就从光标底下漂走。
3. **松手时用世界坐标算矩形**，并**规范化**：从右下往左上拖时 `Rect2` 的尺寸是负的，
   而负尺寸会一路传到排版与命中测试里（症状：区域画出来了，但拖牌进去不认）。
   太小的矩形当误触忽略（手抖一下不该在桌上留下一个点不中、却一直待在存档里的区域）。

`Esc` 或再点一次按钮取消；**关面板时自动收掉模式** —— 不收的话回到桌面
"突然拖不动牌了"，而画布上没有任何东西提示这件事。

### 表单里那条"不许把 A 的值写进 B"的规矩

表单是"回填 + 回调"的组合：换一张卡时要把新值写进控件，而控件收到新值会发
`ValueChanged` / `TextChanged`，回调又会写回定义 —— 那一刻"当前选中的"已经换了人，
于是**旧卡的值被写进新卡**。

处置：`_suppressCallbacks` 在回填期间置真，所有回调一律早退。
这类 bug 只在"连着点两张卡"时出现，肉眼几乎归因不到，所以留了一条断言常驻
（`switching_cards_keeps_names`）。

另一条同源的坑：`LineEdit.Text = "…"` **不会**触发 `TextChanged`
（至少在本项目实测如此）。所以自检里"填一个值"必须显式再调一次回调；
而"用户真的打字"那条路（信号）用另一个走信号的入口来验
（`SetFieldSlotForTest` 走 `OptionButton.ItemSelected`）。

## 4b. 用户报的"打一个字符就失去焦点"

**症状（用户原话）**：部分输入框在输入任意文本之后就失去聚焦，
每次只能输入一个字符，**打五个数字要用鼠标点五次**。

**为什么是"部分"输入框**：只有 Token 页与区域页中招，卡牌页没事 ——
因为那两个页的 `Mutate` 里多调了一次 `RefreshFields()`，而卡牌页没有。

**根因链**（三层，一层比一层隐晦）：

| # | 环节 | 说明 |
|---|---|---|
| 1 | `NotifyChanged()` 每敲一个字符都调 `CurrentPage()?.OnShown()` | 于是每次按键都重刷**整页** |
| 2 | 页的 `OnShown()` 里有 `RefreshList()` | 它**销毁并重建整列按钮** |
| 3 | 页的 `Mutate()` 里还有 `RefreshFields()` | 它把表单里**每个控件的值重写一遍** |

**第 3 层是真凶，而且它的机理反直觉**：

> **把同一个字符串再赋给 `LineEdit.Text`，也会清掉选中区、打断输入法候选。**
> `edit.Text = edit.Text` 不是空操作。

所以"值没变"与"不写"是两件事 —— 而第一版写的
`edit.Text = KeepEditingText(edit, value)` 那个三元表达式**永远会执行那次赋值**：
用户正在输入时它返回 `edit.Text`，于是变成自我赋值。**必须真的跳过那次赋值**
（`ApplyText` 直接带 `if` 返回），而不是"返回一个看起来一样的值"。

**处置**（三条，都是"把两个概念分开"）：

1. **`NotifyChanged()` 只刷顶栏的"未保存"标记**，不再碰任何页的内容。
   谁真的改了**列表结构**（新建 / 删除 / 加删字段），谁自己调那一页的刷新方法。
2. **`Mutate` 里不刷表单。** 模型已经由"正在操作的那个控件"改好了 ——
   刷表单等于把用户刚输入的东西再写一遍。
3. **回填一律走 `ApplyText` / `SetIfChanged`**：值真的不同才写。
   （`SpinBox` / `CheckBox` 被重写同一个值会触发重排与最小尺寸重算，
   而**重排会顺带把焦点从别的控件上摘下来** —— 实测：选中一段文字、再让表单刷一次，
   选中区就没了，而那个值压根没变。）

**这条 bug 是怎么被钉死的**：先加了"改字段不重建列表"（比对象引用）与
"焦点还在时选中区不许消失"两条断言，然后在 `RefreshFields` 里**逐行记录
选中区还在不在**，读数直接指出是"`_name.Text` 那一行"干的：

```
before=有 summary=有 name=无 shape=无 size=无 ...
```

修完再跑，同一串读数变成全"有"。**"把猜换成读"在这一轮又省了半天。**

**一个连带的收获**：改 `NotifyChanged` 的行为时，两条老断言当场变红
（`create_card_appears_in_list` / `drawn_zone_appears_in_list`）——
它们之前是靠"`NotifyChanged` 顺手刷整页"才绿的。
**那正是自检该干的事**：改行为时，依赖旧行为的调用点必须自己暴露出来。

## 5. 抓到的真 bug（这一轮）

| bug | 症状 | 根因 |
|---|---|---|
| `totalCards` 进 JSON | 存档里多一行会漂移的冗余 | `System.Text.Json` 会写只有 getter 的属性；缺 `[JsonIgnore]` |
| **顶栏"未保存"不亮** | 改完卡名，标记还写着「已保存」 | 信号在 `Touch(id)` **之前**发出，订阅者读到的是"没脏" —— 次序反了 |
| **开机刷 7 条 NRE** | 面板看起来完全正常、自检也全绿 | `EditorPage._Ready()` 里调 `OnShown()`；Godot 是子节点先 `_Ready`，那一刻面板页脚的标签还不存在 |
| 桌面背景图从来没生效过 | 填了图片文件名，桌面没变 | `ResourceLoader` 找不到存档目录里的图 |
| 发牌目标下拉是空的 | "刚画好一个牌库，发牌目标里却没有它" | `RefreshTargetPicker` 写了但 `OnShown` 里忘了调 |
| **画区域的遮罩矩形恒为 0** | 拖矩形什么都不发生 | 遮罩挂在<b>隐藏的</b>面板下，而不可见 Control 子树会被跳过布局 |
| **卡面预览是空的** | 面板正常、列表正常，预览框一片灰 | 见下面那一节（两个原因叠在一起） |

### 那条 NRE 值得单独记

它**穿过了全部 16 节、76 条断言**，因为：

- 它发生在**建界面的过程中**（面板 `_Ready` 中途），任何"操作之后读状态"的断言都走不到那里；
- 面板本身完全正常（矩形、分页、列表全对）；
- Godot 把它打成 `ERROR` 到 stderr，而自检读的是 **stdout 的逻辑判定**。

**处置**：`_built` 标志 + 刷新改由 `EditorPanel` 在建完之后统一发起。
另外把 `run.err.log` 里那条完整的 C# 调用栈读出来才定到行 ——
**"日志里有 ERROR"这件事本身不会让任何断言变红**，这是这一轮最值得记的一条：
*判定的覆盖面 = 我想到要问的问题的覆盖面。*

顺带修的一条同类隐患：`RefreshStatus` 与 `NotifyChanged` 现在都挡"面板还没建完"。

### "预览是空的"那一轮

这一条花了最多轮次，值得把过程留下 —— 因为**同一句话底下有三个不同的原因**：

| # | 读到的数 | 真原因 | 处置 |
|---|---|---|---|
| 1 | 预览矩形 `10×7`、颜色数 `1` | 控件在 `VBoxContainer` 里，垂直方向被下面的详情标签吃掉，宽度拿到 **0** | 给 `CustomMinimumSize` 一个明确宽度 |
| 2 | `_Draw` 调用次数 = `0` | 采样是在<b>同一帧内</b>做的：面板刚打开，布局与 `_Draw` 都还没跑，读到的是上一帧的像素 | 采样前 `await` 两帧 |
| 3 | `IsVisibleInTree() == false` | <b>探针自己</b>：前面的分区探针把页签留在了「区域」页，而 `TabContainer` 会把非当前页整体隐藏 | 采样前 `SwitchTab(TabCards)` |

第 3 条最值得记：症状（"预览是一片灰"）与"预览画错了"完全一样，
而根因在**探针自己的前序步骤**上。与 M3 那条「探针找空白点不能猜」同源：
**探针要先把自己弄成被测对象期望的样子。**

最后留下的判据是**几何无关**的一条：在预览矩形里必须能找到与
`CardDefinition.FaceTint` / `BackTint` 相符的填充像素。
实测正面 25192 个取样点里 22624 个差值 ≤10、最近差值 `0`。
前面试过"两面主色不同"—— 实测只差 19，阈值怎么定都站不住
（宽了是假绿、紧了会随卡面样式假红），所以换掉了。

### 一条"我差点自己骗自己"

有一次 `dotnet build` 失败了（`SaveJson.Quantize` 不存在，它其实在 `ColorJsonConverter` 上），
而我把构建输出用 `Select-String` 过滤掉了，于是**看到 `[run] OK` 就以为改动生效了**，
跑出来的其实是上一版二进制。

处置：跑自检的命令改成 `if ($LASTEXITCODE -eq 0) { ... }` 门控，
并在改动后核对 `.godot/mono/temp/bin/Debug/TabletopSimulator.dll` 的时间戳。
**"跑通了"必须包含"跑的是我刚写的那份代码"。**

## 5b. M5.5 P1：用户实测反馈里的前三条

用户 2026-09-21 实测后报了 6 条可用性缺口，整理成 `docs/m5-5-usability-plan.md`（P1–P4）。
本轮做了 **P1** 的三条 —— 都是"改完立刻能感觉到"且不动数据结构的。

### 5b-1. F1 的可点入口 + `Esc` 两级关闭

**问题**：编辑器原先只有快捷键一条入口，刚进来的人不知道它怎么开；
而 `Esc` **关不掉**面板 —— 面板打开时 `_UnhandledKeyInput` 把其余按键一律吃掉并标记已处理，
`Esc` 只被"画区域"模式用（退出那个模式），永远轮不到关闭面板。

**处置**：

| 改动 | 说明 |
|---|---|
| `Hud.EditorButton` | 顶栏「编辑器　F1」按钮，挨着「存档 ▾」（`Hud` 只管发 `EditorToggleRequested`，**不依赖 `EditorPanel` 类型** —— 与 M4 的 `SaveRequested` 同一套路） |
| 按钮文字随状态变 | `编辑器　F1` ↔ `关闭编辑器　Esc`。它是个普通按钮、不是开关，**按下去没有任何视觉反馈**，文字是唯一的提示 |
| `HandleEscape` | 两级：先收"画区域"模式、再关面板；判断**排在"吃掉其余按键"之前**（否则永远轮不到它） |
| 遮罩层不再自己处理 `Esc` | 它在 `_Input` 里跑在 `_UnhandledKeyInput` **之前** —— 本层一旦把事件吃掉并标记已处理，面板那一层就永远收不到。改成转交 `EditorPanel.HandleEscape`，退出逻辑只剩一处实现 |
| **正拖着矩形时那一下 `Esc` 不算** | 那一下的本意是"放弃这一块"，而面板若在拖拽中途关掉，遮罩层会连拖动状态一起清 —— 看起来像"拖到一半界面闪了一下" |
| 画区域模式的光标变十字 | 那层 5% 的淡色遮罩在深色桌面上几乎看不出来，而"忘了自己还开着它"是这个模式唯一的风险 |

### 5b-2. 卡牌页缺"新建 / 复制 / 删除"入口

**这一条要特别记**：`CardDefinitionService.CreateCard` / `DeleteCard` **从 M5 起就在**，
自检也一直在调用它们 —— **缺的只有入口**。用户报的是"根本没有新建、删除卡牌的功能"，
他的感受完全正确，而原因不是"没做功能"。

> **入口不可发现 ≠ 功能缺失，但用户的体感没有区别。**
> 同一个模式在"区域不能删除"那条上也出现过（删除按钮藏在页面左下角，用户同样没找到）。

服务层新增 `DuplicateCard` / `DuplicateToken`，**都走同一把 `UniqueId`**
（另写一套判重的话，删掉再复制就会撞上"存档里那张旧卡还引用着的 id"）。
复制走 `CardDefinition.Clone()` 的深拷贝，名字加「副本」后缀 ——
列表按 id 排序，两张同名的卡在列表里挨不到一起，用户会以为复制失败。

指示物页原先已有新建/删除，本轮补上「复制这个」，两页现在是同一套动作。

### 5b-3. 指示物预览里四个形状"歪了"

**根因**（用户报的原话是"4 个形状的图标位置是歪的，不在框里"）：

```csharp
var local    = new Rect2(cell.Position + (cell.Size * 0.5f), cell.Size);
var centered = new Rect2(-cell.Size * 0.5f, cell.Size);   // ← 以原点为中心
DrawSetTransform(local.GetCenter(), 0f, Vector2.One);     // ← 已经把原点挪到格子中心了
TokenFaceRenderer.Draw(this, probe, centered, "");        // ← 于是又平移了半个格子
```

**平移做了两次**，圆心落到"格子中心 + 半个格子"，而形状框画在格子上。改成只平移一次。

顺带把"逐个属性抄一份 `probe`"改成 `_definition.Clone()` 再改 `Shape` ——
抄一份的话，Token 以后加字段（比如"旋转 15°"）会**静默漏掉**：
预览照旧画，只是永远不反映那个新字段，而没有任何地方会报错。

### 这一轮最值得记的三条

**1. 断言要量"面积"，不要量"一个点"。**

第一版写的判据是"格子正中心那个像素应当是填充色"，结果四种形状**全红** ——
**而产品是对的**：中心的文字（`"1"`）正好画在那儿，取到的是文字色（实读 `#ffffff`）。
`token 上有字` 被判成了 `形状歪了`。

> **一个取样点的断言，会把"那一点上恰好有别的东西"当成几何错误。**

改成两条互补的判据：本格里的填充像素数 ≥ 该形状**理论面积**的 40%
（圆 πr²、内接正方形 2r²、正六边形 2.598r²、正三角形 1.299r²），
以及**邻格中心不许有本形状的填充**（那正是"歪了一格"的特征）。
实测三角形的填充量 `1218` 与理论值 `1218` 完全吻合 —— 判据是真的在量几何。

**2. 合成输入必须"排出去、收干净"，否则它会落在别的探针头上。**

新加的入口探针里 `PushKey(Esc)` 之后直接断言，**没等一帧**。
而 `Input.ParseInputEvent` 发的是"按下 + 松开"两个事件、**一帧只派发一个**，
于是那个"松开"留在队列里，等到十几步之后才派发 ——
症状是**卡面预览整个变黑**（那会儿面板被别人关了），而根因在两节之外。

这与 M4 那条「探针不许改变被测对象的状态」同源。处置：新增
`DevInputSim.PushKeyAndSettle`（按下 + 等两帧）。

**3. 顺带发现：喂合成键去验"按键处理逻辑"本身不可靠。**

即使 `PushKeyAndSettle` 修好了队列，`Esc` 的四条断言仍然时红时绿：
`HandleEscape` 明明把面板关掉了（读数 `open=False`），
而两帧之后面板又是开的 —— 同一个 `Esc` 在引擎的输入分发里会落到别的节点上再被处理一次，
读出来的状态**取决于帧数而不是产品逻辑**。

处置：这几条改成**直接喂引擎真正会转交的那个事件对象**
（`editor._UnhandledKeyInput(EscapeEvent())` / `editor.Overlay._Input(...)`），
验的是"收到 `Esc` 之后怎么处理"；**输入分发本身**由 `DevInputSim` 的其它节负责验。
两条路各验各的，比一条路验两件事更硬。

### 一条老坑换了张脸：备份还原会骗过 `dotnet build`

回退验证时用 `Copy-Item` 还原被改坏的文件，而**文件的时间戳没变**
（原来的 mtime 被保留），于是 `dotnet build` 判定"没有变化"、**继续跑旧的 DLL**。
症状是"回退验证之后修复好像失效了"，连查两轮都是同一个红灯。

处置：**还原文件之后一律 `dotnet build --no-incremental`**。
与 M5 那条「跑通了必须包含"跑的是我刚写的那份代码"」是同一件事的第三种长相。

四条元规矩：

1. **探针自己收拾自己。** 开场抓 `SceneSnapshot`，`finally` 里写回去，
   断言 `table_restored` 与 `invariants_after_probe`。临时文件、临时存档、改过的版式都还回去。
2. **"没条件跑"和"跑挂了"长得不一样。** 编辑器没建起来时**不写 `pass` 键**，写 `skipped`。
3. **探针要先把自己弄成被测对象期望的样子。** 读像素之前先切到卡牌页、先等两帧 ——
   否则量到的是上一个分页、上一帧。
4. **断言的前置不成立时，要看得见。** `field_slot_was_different_before`
   第一次就是红的 —— 因为新建字段的默认槽位恰好**就是**它要改去的那个。
   单点断言"改完对不对"会给出一个永远为真的绿灯；**前置断言**才逼你看清这件事。
5. **（M5.5 P1 新增）量"面积"，不要量"一个点"。**
   "格子中心那一个像素是填充色"这条判据把"token 上有字"判成了"形状歪了" ——
   **四个形状全红而产品是对的**。改成一个区域里的**像素计数**之后，
   判据变得与"那一点上恰好有什么"无关，并且能直接与理论几何值对照。
6. **（M5.5 P1 新增）排出去的合成输入必须自己收干净。**
   合成键是"按下 + 松开"两个事件、一帧只派发一个；按完就断言，
   那个残留事件会落到**十几步之后**的另一段探针头上（症状：卡面预览整个变黑）。
   用 `DevInputSim.PushKeyAndSettle`。
7. **（M5.5 P1 新增）验"按键处理逻辑"时直接喂事件对象，不要绕引擎分发。**
   绕分发时读出来的状态**取决于帧数**而不是产品逻辑（同一个 `Esc` 会落到别的节点上）。
   把"怎么处理"与"分发到没到"拆成两条路各验各的。

### 反例是必须的

"删不掉"这条断言如果不配一个"空定义删得掉"的反例，
它可能只是因为删除功能**整个坏了** —— 而断言照样全绿。
所以 `delete_unused_card_succeeds` 与 `delete_in_use_card_refused` 成对存在。

同一条道理在这一轮又出现一次：`token_delete_allowed_after_cleanup` 第一次是红的，
因为**示例内容本身就在桌上放了两个指示物**用着那份定义 —— 我的"干净了"前提是假的，
而产品是对的。改法不是放宽断言，而是换一个前提完全由自己控制的定义（新建的）来验。

M5.5 P1 又添两处同一道理的用法：
**"复制是深拷贝"必须配"改副本、原卡不许变"**（只比"值相等"的话，共享引用也能全绿），
以及**"邻格不许有填充"与"本格必须有填充"成对**（只留一条的话，
"图形小到看不见"与"图形歪到隔壁"会互相掩护）。

## 7. 重启实测

M5 改的是**定义**那一半（`project.json`），所以"关掉再打开还在不在"是它最该被验的一件事。
`godot_run.ps1` 每次清空存档根 + 强制 `--fresh`（判定跑要确定的基准），
所以这一步在它外面手工跑一遍 —— **不带 `--fresh`**，让它读回上一局写的档。

第二局读回来的东西（与 `docs/STATUS.md` 里那份表同源）：

| 项 | 结果 |
|---|---|
| 物件 / 区域 | 36 件（卡 32 / 骰 2）；牌库 20 张 —— 与第一局结束时一致 |
| 八条区域不变量 | 全绿 |
| `project.json` 的卡组段 | 1 副「示例卡组」共 20 张 |
| 卡牌定义段的字段与版式 | 字段数 3、版式卡名字号 34 —— 都读回来了 |
| `editor_simulation` | 164 条全过（编辑器在"读回来的存档"上照样能用，含端到端那一步的"开玩"） |
| restart 日志 | `NullReference` / `Unhandled` / `SCRIPT ERROR` 0 条 |

**这一条的意义**：前面那些断言验的是"编辑器能不能改对"，
而重启验的是"改对的东西**留没留住**"。两件事都属"能用了"，但只有后者需要跨进程。
M4 那轮就是靠重启实测抓到"读档后牌库成员表是空的"——同一类问题在 M5 上的表现会是
"卡组读回来少了张数""字段读回来是空的"，而它们在单进程的自检里全都看不出来。

### 端到端那一条为什么要走到"真的抽一张牌"

名字里写着"开玩"的那一节，第一版**把牌发进牌库就去做存盘核对了** ——
一步牌都没玩。那验的是"内容造出来了"，不是"造出来的东西能玩"。

补上的那一步：画一块手牌区 → **用区域页的表单**把牌库的抽牌目标指过去 →
`TryHandleDoubleClick` 抽一张 → 翻面 → 换排版 → 撤销两步 → 复查八条不变量。

两个附带的好处：

- **它验的是"编辑器能改一个<b>有成员的活区域</b>"**。区域编辑最容易错的地方就在这儿：
  改完要 `ApplyLayout`，而成员的位置与次序都得跟着重排 —— 改一个空区域不会暴露任何问题。
- **它把"抽牌"这条路的两个上游接了起来**：`DrawTargetId` 是编辑器设的，
  而抽出来的牌是 `zone.Top`，也就是**编辑器设的那个目标真的被 `ResolveDrawTarget` 认了**。

实测读到的数：`牌库 4 · 手牌 1 · 抽出的是 card-0053`（发进去 5 张，抽走 1 张，剩 4 张）。

### 用户实测反馈的 6 条可用性缺口

但**没有任何东西约束物件与区域待在桌子内**。用户说"那画布没有作用"是准确的。
这一条要等 P3 拍板之后才有解。
